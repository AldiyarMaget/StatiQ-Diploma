# Literature Review: Retrieval-Augmented Generation, Semantic Routing, and Structured API Ingestion

## 1. Introduction & Theoretical Foundations

Retrieval-Augmented Generation (RAG) has become the definitive architectural paradigm for grounding Large Language Models (LLMs) on private, domain-specific, and dynamically updated enterprise knowledge repositories. Deploying RAG within distributed enterprise IT environments introduces two fundamental engineering challenges:
1. **Multi-Modal Data Heterogeneity:** Enterprise knowledge is structurally divided between semi-structured narrative guidelines (Markdown, DOCX, regulatory manuals) and deeply nested, machine-readable interface specifications (OpenAPI 3.0 / Swagger JSON schemas).
2. **Retrieval Precision Trade-offs:** Dense vector proximity search captures broad semantic intent but exhibits severe degradation on exact alphanumeric identifiers (e.g., HTTP status codes, routing keys, parameter names). Conversely, sparse lexical search resolves exact tokens but lacks semantic abstraction.

This review critically evaluates 15 authoritative sources — comprising 10 high-tier peer-reviewed publications (NeurIPS, IEEE TPAMI, ACM SIGIR, ICLR, USENIX OSDI, EACL, TMLR), 4 technical preprints/surveys (arXiv), and 1 industry standard (OpenAPI Initiative). In accordance with academic guidelines, the core body of literature is selected from the last 5 years (2021–2024), while strictly retaining essential foundational works (Cormack et al., 2009; Lewis et al., 2020; Malkov & Yashunin, 2020) that theoretically underpin RAG, HNSW graph indexing, and Reciprocal Rank Fusion.

## 3. Critical Synthesis & Research Gaps

A systematic analysis of the 15 publications reveals four primary engineering challenges that compromise conventional RAG implementations in enterprise documentation environments:

### 3.1. The Structural Chunking Dilemma in Machine-Readable Contracts
Conventional RAG frameworks (Lewis et al., 2020; Gao et al., 2023) rely on naive sliding-window text chunking (e.g., fixed-token windows with overlap). When applied to structured OpenAPI specifications (OpenAPI Initiative, 2020), naive chunking destroys hierarchical trees, severing HTTP verbs from endpoint paths and breaking `$ref` object references. While ToolLLM (Qin et al., 2024) and Gorilla (Patil et al., 2024) confirm the necessity of API-level retrieval, they rely on complex neural models or weight fine-tuning. Furthermore, abstractive summarization approaches such as RAPTOR (Sarthi et al., 2024) flatten technical specifications and blur exact parameter names.

**Design Implications for StatIQ:** The system design must incorporate a dedicated Abstract Syntax Tree (AST) chunker for OpenAPI specifications. Rather than treating specifications as raw text, the planned parser will segment contracts into atomic semantic units where HTTP methods, route paths, parameter schemas, and response models remain structurally coupled.

### 3.2. Lexical Degradation of Pure Dense Retrieval on Exact Identifiers
State-of-the-art dense embeddings such as E5 (Wang et al., 2022) and Contriever (Izacard et al., 2021) provide superior semantic generalization across natural-language queries. However, empirical literature indicates that dense embeddings exhibit performance degradation when queries contain exact alphanumeric tokens, such as HTTP status codes, numeric process state identifiers, or specific parameter keys. Dense proximity search treats these tokens as arbitrary low-frequency points, causing semantic drift.

**Design Implications for StatIQ:** To prevent lexical drift, the system architecture requires a hybrid retrieval pipeline. PostgreSQL's native lexical search engine (`tsvector` with inverted indexing) will run in parallel with dense vector search (`pgvector` with HNSW indexing; Malkov & Yashunin, 2020). The candidate lists will be fused using Reciprocal Rank Fusion (Cormack et al., 2009), augmented with schema-aware ranking heuristics to prevent cross-domain contamination.

### 3.3. Contextual Noise and Prompt Contamination
Modular RAG surveys (Gao et al., 2023) emphasize that injecting non-relevant documentation into an LLM context window causes hallucination and parameter drift. While self-correcting methods such as Self-RAG (Asai et al., 2024) and CRAG (Yan et al., 2024) introduce reflection loops or external search fallbacks, they introduce significant latency and violate corporate data privacy.

**Design Implications for StatIQ:** The architecture requires a lightweight, in-process semantic intent routing layer. By classifying incoming query embeddings against domain anchor clusters prior to search execution, the system will deterministically restrict search execution to target document partitions, preventing cross-domain context contamination without external reflection overhead.

### 3.4. Unified Storage vs. Dual-Database Synchronization Overhead
Deploying an isolated vector database alongside an enterprise relational database introduces transactional complexity, multi-system latency, and dual-state synchronization vulnerabilities.

**Design Implications for StatIQ:** Supported by the theoretical findings of VBASE (Zhang et al., 2023), the proposed architecture adopts a unified storage model: PostgreSQL 16 with `pgvector`. This consolidates relational metadata, inverted text indexes, and HNSW vector graphs into a single ACID-compliant database engine.

## 4. Conclusion & Implications for StatIQ Architecture

The synthesized literature directly establishes and justifies the theoretical foundations for the upcoming development stages:
1. **System Categorization:** StatIQ is theoretically positioned within the **Modular RAG** paradigm (Gao et al., 2023).
2. **Unified Storage Baseline:** PostgreSQL 16 with `pgvector` will serve as the unified engine, ensuring transactional consistency across metadata and vector embeddings (Malkov & Yashunin, 2020; Zhang et al., 2023).
3. **Pre-Retrieval Routing:** Semantic intent classification is established as a design requirement to eliminate context contamination prior to database querying (Wang et al., 2022; Asai et al., 2024).
4. **Empirical Benchmarking Protocol:** The verification methodology will adopt metrics established by Ragas (Es et al., 2024) and classical information retrieval theory (Mean Reciprocal Rank, Recall@K), providing an objective basis for comparing the planned hybrid pipeline against a standard dense baseline (Lewis et al., 2020).
